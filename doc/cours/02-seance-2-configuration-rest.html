CONFIGURATION · LE PROBLÈME

Une règle métier enfouie dans le code

item/ItemService.java
public Item create(Item item) {
    if (items.countByOwnerId(item.getOwnerId()) >= 20) {
        throw new IllegalStateException("Trop d'objets");
    }
    return items.save(item);
}
Pourquoi 20 ? Personne ne le sait dans six mois. Et si le client veut 50 en production et 3 pour les tests, il faut modifier le code, recompiler et redéployer.
04

Règle métier choisie pour la séance : un utilisateur ne peut pas proposer plus de N objets différents. C'est elle que les groupes externaliseront dans le TP 3.

Demander à la salle : « qui décide de ce 20 ? » → le client, pas le développeur. Une valeur qui peut changer sans que le code change n'a rien à faire dans le code.

Même raisonnement que l'évolution 2 de la séance 1 : on veut changer un comportement sans toucher aux classes.

05

Le fichier existe déjà dans le projet généré à la séance 1, il était vide (ou ne contenait que spring.application.name).

Préfixer ses propres clés (ici troc.) évite toute collision avec les clés de Spring. Les tirets (max-per-user) sont la convention recommandée.

Deuxième règle, troc.trade.max-pending : nombre maximum de trocs en attente par utilisateur. Elle servira au TP 4.

CONFIGURATION · @VALUE

Lire une valeur : @Value

item/ItemService.java
@Service
public class ItemService {
    private final ItemRepository items;
    private final UserRepository users;
    private final int maxPerUser;

    public ItemService(ItemRepository items, UserRepository users,
                       @Value("${troc.item.max-per-user:20}") int maxPerUser) {
        this.items = items;
        this.users = users;
        this.maxPerUser = maxPerUser;
    }

    public Item create(Item item) {
        if (items.countByOwnerId(item.getOwnerId()) >= maxPerUser) { ... }
${clé:défaut} : la valeur vient du fichier, 20 si la clé est absente. Spring convertit le texte en int tout seul.
06

La valeur arrive par le constructeur, exactement comme le repository : c'est de l'injection de dépendances. Une valeur de configuration est une dépendance comme une autre.

Si la clé est absente et qu'il n'y a pas de valeur par défaut, l'application refuse de démarrer, avec un message explicite (même comportement qu'un bean introuvable en séance 1).

Une faute de frappe dans la clé ne provoque aucune erreur à la compilation : c'est la limite de @Value, et la transition vers la diapo suivante.

CONFIGURATION · @CONFIGURATIONPROPERTIES

Regrouper des réglages : @ConfigurationProperties

item/ItemProperties.java · TrocApplication.java · item/ItemService.java
@ConfigurationProperties("troc.item")                // préfixe des clés
public record ItemProperties(int maxPerUser) { }     // max-per-user → maxPerUser

@SpringBootApplication
@ConfigurationPropertiesScan                         // détecte les @ConfigurationProperties
public class TrocApplication { ... }

@Service
public class ItemService {
    private final ItemProperties props;              // un bean comme un autre
    public ItemService(ItemRepository items, UserRepository users,
                       ItemProperties props) { ... }
    // ... props.maxPerUser()
}
@Value pour une valeur isolée ; @ConfigurationProperties dès qu'un groupe de réglages apparaît : typé, rangé dans sa fonctionnalité, injecté par constructeur.
07

Le record déclare la forme des réglages ; Spring lit toutes les clés troc.item.* et remplit le record. La conversion de max-per-user en maxPerUser est automatique.

Rangement par fonctionnalité, comme le reste du projet : ItemProperties dans item/, TradeProperties dans trade/.

Avantage pratique : une seule classe à lire pour connaître tous les réglages d'une fonctionnalité, et l'IDE propose l'autocomplétion dans le code.

REST · RAPPEL

Ce que vous savez déjà

  • Des ressources des noms au pluriel : /users, /items/7, /trades
  • Un verbe par intention GET lit · POST crée · PUT remplace · DELETE supprime
  • Où va l'information chemin : une ressource · ?param : un filtre · corps : les données
  • Les codes 200 · 201 · 204  |  400 · 404 · 409  |  500 = un bug
  • 400 ou 409 ? invalide en soi → 400 · valide, mais l'état des données s'y oppose → 409
10

Seul point à appuyer : 400 ou 409. Le choix fait partie des choix techniques à justifier à l'évaluation, et il revient dans les deux blocs du TP.

Une action métier (proposer un troc) reste la création d'une ressource : POST /trades. Ce sera le bloc 2.

REST · DANS LE CODE

Chemin, paramètre, corps : les annotations

item/ItemController.java
@RestController
@RequestMapping("/items")                               // préfixe commun à toutes les méthodes
public class ItemController {
    // ... constructeur : ItemService injecté, comme en séance 1

    @GetMapping("/{id}")                                  // GET /items/7
    public Item findById(@PathVariable Long id) { return itemService.findById(id); }

    @GetMapping                                          // GET /items?ownerId=42
    public List<Item> findAll(@RequestParam(required = false) Long ownerId) {
        return itemService.findAll(ownerId);                 // ownerId null = tous
    }

    @PostMapping                                         // POST /items + JSON
    public Item create(@RequestBody Item item) { return itemService.create(item); }
}
Le nom du paramètre Java fait le lien : {id} ↔ Long id, ?ownerId= ↔ Long ownerId.
11

Le verbe et le chemin se déclarent avec @GetMapping, @PostMapping, @PutMapping, @DeleteMapping. @RequestBody a déjà été vu en séance 1 sur POST /users : les nouveautés sont @PathVariable et @RequestParam.

@RequestMapping sur la classe évite de répéter /items sur chaque méthode. Proposer aux groupes de faire la même chose sur UserController.

Par défaut, un @RequestParam est obligatoire : sans required = false, GET /items sans paramètre renverrait 400.

Si on appelle GET /items/abc, Spring ne peut pas convertir « abc » en Long : réponse 400 automatique, sans une ligne de code.

REST · CODES DE STATUT EN SPRING

Choisir son code de statut

user/UserController.java · user/UserService.java
@PostMapping                                                 // UserController
public ResponseEntity<User> create(@RequestBody User user) {
    User saved = userService.create(user);
    return ResponseEntity.created(URI.create("/users/" + saved.getId()))   // 201 + Location
                         .body(saved);
}

@DeleteMapping("/{id}")
@ResponseStatus(HttpStatus.NO_CONTENT)                          // 204, sans corps
public void delete(@PathVariable Long id) { userService.delete(id); }

public User findById(Long id) {                                // UserService
    return users.findById(id).orElseThrow(() ->
        new ResponseStatusException(HttpStatus.NOT_FOUND, "Utilisateur " + id + " introuvable")); // 404
}
12

Rappel de la séance 1 : notre POST /users renvoyait 200. Voici comment renvoyer le 201 attendu, avec l'en-tête Location qui indique où trouver la ressource créée.

Trois outils : ResponseEntity quand le code ou les en-têtes dépendent du cas ; @ResponseStatus quand le code est toujours le même ; ResponseStatusException pour interrompre le traitement avec une erreur.

Limite assumée : ResponseStatusException dans le service mélange un peu web et métier. Le bonus @ControllerAdvice permet de lancer une exception métier (NotFoundException) et de la traduire en 404 côté web.

Le TP fait passer findById à Optional (TP 2, mise en place) : le code de la diapo est celui que les étudiants écrivent.

Pour vérifier les codes : la collection Bruno du projet, ou curl -i (sans -i, curl n'affiche ni le code ni les en-têtes).

CHECKPOINT #1 · PIÈGES COURANTS

Ça ne marche pas : que dit la réponse ?

  • 415 Unsupported Media Type en-tête Content-Type: application/json oublié
  • 400 Bad Request JSON mal formé, ou /items/abc au lieu d'un nombre
  • 405 Method Not Allowed bon chemin, mauvais verbe : méthode non mappée
  • Un champ arrive à null nom JSON ≠ nom Java, ou setter manquant
  • Un champ manque en sortie getter manquant : seul ce qui est exposé est converti
15

Message à faire passer : le code de statut est le premier outil de diagnostic. Lire le code avant de relire son propre code.

La conversion JSON ↔ Java est faite par la bibliothèque Jackson, incluse avec Spring Web. Elle passe par les getters et setters (ou le constructeur d'un record).

Penser aussi à la console de l'application : Spring y journalise la raison précise d'un 400.
