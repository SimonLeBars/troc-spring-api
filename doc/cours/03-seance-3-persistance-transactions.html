PERSISTANCE · CHOIX TECHNIQUE

Spring Data JDBC plutôt que JPA

  • On écrit le schéma CREATE TABLE à la main : PK, FK et index restent sous vos yeux
  • Pas de magie cachée save() écrit, findById() lit : pas de cache ni de chargement différé
  • SQL prévisible une méthode appelée = des requêtes que l'on peut deviner
  • Ce qu'on perd relations objet automatiques : on manipule des identifiants (ownerId)
  • Pour ce cours la note porte sur les concepts SQL : autant qu'ils restent visibles
05

JPA/Hibernate est très répandu en entreprise et reste un bon choix. Mais il génère le SQL, suit les objets modifiés et les enregistre « tout seul » en fin de transaction : puissant, mais déroutant pour une première approche.

Avec Spring Data JDBC, un objet modifié n'est enregistré que si on appelle save(). Rien ne se passe dans votre dos.

C'est un exemple de choix technique justifié, exactement ce qu'on attend d'eux dans le projet : une alternative, un critère, une décision.

06

H2 est une base écrite en Java, embarquée dans l'application : rien à installer. Le même code tournerait sur PostgreSQL en changeant la dépendance et l'URL (et, idéalement, en passant le mot de passe par variable d'environnement, cf. séance 2).

spring.sql.init.mode=always : par défaut, Spring Boot n'exécute schema.sql que pour une base en mémoire. Avec une base fichier, il faut le demander.

Console H2 : depuis Spring Boot 4, elle est dans un module séparé, spring-boot-h2console. Sans lui, /h2-console répond 404. Se connecter avec exactement la même URL JDBC que dans le fichier, option comprise.

CASE_INSENSITIVE_IDENTIFIERS=TRUE : Spring Data JDBC met les noms entre guillemets ("users"), donc sensibles à la casse, alors que H2 a rangé le CREATE TABLE users sans guillemets sous le nom USERS. Sans l'option : 500, « Table "users" not found (candidates are: "USERS") ». Option propre à H2 : le code Java, lui, reste compatible PostgreSQL.

Ajouter data/ au .gitignore : la base n'a rien à faire dans git.

PERSISTANCE · LE SCHÉMA

Trois tables, reliées par des clés étrangères

07

Toutes les flèches pointent vers une clé primaire : une clé étrangère dit « cette valeur doit exister là-bas ». Impossible d'enregistrer un objet dont le propriétaire n'existe pas, même avec un bug dans le code.

trades référence deux fois users et deux fois items : c'est normal, un troc a deux participants et deux objets.

CHECK et UNIQUE : on y revient au checkpoint #1, ce sont des filets de sécurité qui serviront pendant l'expérience du bloc 2.

PERSISTANCE · SCHEMA.SQL

Le schéma s'écrit en SQL, à la main

src/main/resources/schema.sql
CREATE TABLE IF NOT EXISTS users (
    id        BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    name      VARCHAR(100) NOT NULL
);

CREATE TABLE IF NOT EXISTS items (
    id        BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    owner_id  BIGINT NOT NULL REFERENCES users(id),
    name      VARCHAR(100) NOT NULL,
    quantity  INT NOT NULL CHECK (quantity >= 0),
    UNIQUE (owner_id, name)
);

-- trades : même principe, 4 clés étrangères, status VARCHAR(20) NOT NULL
IF NOT EXISTS : le script est rejoué à chaque démarrage, il ne doit pas échouer si la table existe déjà.
08

IDENTITY : c'est la base qui attribue l'identifiant à l'insertion. Fini le compteur Java des repositories en mémoire.

La table s'appelle users et non user : USER est un mot réservé en SQL (et dans H2). Erreur classique, elle reviendra au checkpoint.

Corollaire de IF NOT EXISTS : modifier une table existante ne marchera pas en éditant le CREATE. Pendant le cours, le plus simple est de supprimer le dossier data/ et de redémarrer. En entreprise, on utiliserait un outil de migration (Flyway, Liquibase).

public interface ItemRepository
    extends ListCrudRepository<Item, Long> {

    // requêtes déduites du nom de la méthode
    List<Item> findByOwnerId(Long ownerId);

//           deleteById, count…
ownerId devient owner_id tout seul. Spring lit le nom findByOwnerIdAndName et en déduit le WHERE.
09

save() décide seul entre INSERT et UPDATE : id null → INSERT (et l'id généré est renseigné dans l'objet retourné), id non null → UPDATE.

On garde Long ownerId et non un objet User : Spring Data JDBC travaille avec des identifiants entre agrégats. C'est voulu, et ça correspond exactement à la colonne owner_id.

Pour une requête impossible à exprimer par un nom de méthode : @Query("SELECT …") sur la méthode. Ce sera un bonus.

L'enum TradeStatus est stocké en texte dans la colonne status, sans configuration.

TRANSACTIONS · LE MÉTIER

Un troc, deux accords

POST /trades/{id}/accept et POST /trades/{id}/reject, avec le destinataire dans le corps : { "userId": 2 }.
12

Proposer, c'est déjà donner son accord ; accepter, c'est le second accord. L'exécution a lieu au moment de l'acceptation : pas d'état intermédiaire « accepté mais pas encore échangé ».

accept et reject : des actions métier modélisées comme des sous-ressources en POST, dans l'esprit de la diapo « Concevoir ses URLs » de la séance 2.

userId dans le corps, comme proposerId en séance 2 : faute d'authentification, le client se déclare. Si ce n'est pas le destinataire : 403 Forbidden. Si le troc n'est plus PROPOSED : 409.

TRANSACTIONS · LE PROBLÈME

Accepter un troc, c'est cinq écritures

13

Pourquoi l'étape 3 échoue-t-elle ? Bob avait 5 carottes à la proposition, il en a donné 4 ailleurs entre-temps. Le stock a changé entre la proposition et l'acceptation : il faut revérifier au moment d'exécuter.

Ici c'est la contrainte CHECK (quantity >= 0) qui refuse l'écriture. Dans un bon code, la vérification est faite avant toute écriture (diapo suivante) ; la contrainte est le filet si le code se trompe.

Une panne réseau, un crash, un bug dans le crédit produiraient le même état incohérent. La transaction couvre tous ces cas, pas seulement ceux qu'on a prévus.

Ordre réel du code de référence : chaque transfert débite puis crédite (l'objet offert, puis l'objet demandé). C'est exactement ce qu'on observe dans l'expérience du bloc 2 : Alice à 7 tomates, une ligne « tomates » à 3 chez Bob, troc toujours PROPOSED.

TRANSACTIONS · @TRANSACTIONAL

Une annotation, une méthode, une transaction

trade/TradeService.java
@Transactional                                               // BEGIN … COMMIT ou ROLLBACK
public Trade accept(Long tradeId, Long userId) {
    Trade trade = findById(tradeId);                            // 404
    checkAcceptable(trade, userId);                             // 403 ou 409

    Item offered   = itemService.findById(trade.getOfferedItemId());
    Item requested = itemService.findById(trade.getRequestedItemId());
    checkStock(offered,   trade.getOfferedQuantity());          // 409, AVANT toute écriture
    checkStock(requested, trade.getRequestedQuantity());

    itemService.transfer(offered,   trade.getOfferedQuantity(),   trade.getRecipientId());
    itemService.transfer(requested, trade.getRequestedQuantity(), trade.getProposerId());

    trade.setStatus(TradeStatus.EXECUTED);
    return trades.save(trade);
}
itemService.transfer : débit de l'objet, crédit de l'autre. Une exception sort de la méthode ? Rien n'est enregistré.
14

L'annotation va sur le service : c'est lui qui connaît l'opération métier complète. Ni sur le contrôleur (trop haut), ni sur chaque méthode du repository (trop bas, chaque écriture aurait sa propre transaction).

checkAcceptable et checkStock lancent des ResponseStatusException : ce sont des RuntimeException, donc elles déclenchent aussi le rollback. Ici, rien n'a encore été écrit, mais la règle reste la même.

transfer est dans ItemService (il manipule des objets) et appelle items.save directement : ItemService.update refuserait un stock qui tombe à 0. Pas besoin de @Transactional dessus : il rejoint la transaction ouverte par accept.

Crédit : chercher la ligne (owner, name) avec findByOwnerIdAndName ; si elle existe on ajoute la quantité, sinon on crée une nouvelle ligne. Question à poser aux groupes : la création d'une ligne doit-elle respecter troc.item.max-per-user ? C'est un choix à justifier.

TRANSACTIONS · SOUS LE CAPOT

Spring s'intercale entre l'appelant et votre méthode

Le contrôleur croit appeler TradeService : il reçoit en fait un proxy, injecté par le conteneur vu en séance 1.
15

C'est le conteneur IoC qui rend ça possible : comme c'est lui qui crée et injecte les beans, il peut injecter un « emballage » autour de TradeService plutôt que l'objet lui-même.

Teaser pour la séance 4 : ce mécanisme d'interception, c'est de la programmation orientée aspect. @Transactional est un aspect fourni par Spring ; jeudi prochain, on écrira le nôtre pour journaliser les trocs.

TRANSACTIONS · LES PIÈGES

Quand @Transactional ne fait rien

  • Appel interne this.accept() depuis la même classe ne passe pas par le proxy
  • Exception vérifiée par défaut, seule une RuntimeException déclenche le rollback
  • try / catch avalé une exception rattrapée dans la méthode : le proxy ne la voit pas, il valide
  • Méthode non publique l'annotation doit être sur une méthode publique d'un bean
  • La règle simple sur la méthode publique du service, appelée par le contrôleur
16

Les trois premiers pièges ont la même cause : le proxy de la diapo précédente. S'il n'est pas traversé, ou s'il ne voit pas l'exception, il n'y a rien à annuler.

Exception vérifiée (une sous-classe d'Exception) : la transaction est validée malgré l'erreur. Pour changer ce comportement : @Transactional(rollbackFor = Exception.class). Dans notre projet, ResponseStatusException et les exceptions de la base sont des RuntimeException.

Garder la transaction courte : pas d'appel réseau ni d'attente à l'intérieur, elle bloque des lignes pendant ce temps.

CHECKPOINT #1 · CONTRAINTES ET INDEX

Le code vérifie, la base garantit

  • FOREIGN KEY supprimer un utilisateur qui a des objets est refusé : 409 ou suppression en cascade ?
  • CHECK ≥ 0 aucun stock négatif, même si le code oublie une vérification
  • UNIQUE une seule ligne « tomates » par utilisateur : le crédit ajoute à l'existante
  • INDEX GET /trades?userId= lit trades par participant : à indexer
  • À justifier chaque contrainte et chaque index : c'est noté dans le projet
20

FK : DELETE /users/1 alors qu'il possède des objets → la base lève une exception d'intégrité → 500 si on ne fait rien. Aux groupes de choisir : vérifier et renvoyer 409, ou supprimer d'abord ses objets. Les deux se défendent.

Index : CREATE INDEX IF NOT EXISTS idx_trades_recipient ON trades(recipient_id); idem sur proposer_id. Un index accélère les lectures mais ralentit un peu les écritures : on indexe ce qu'on interroge. Selon le SGBD, une clé étrangère n'est pas indexée automatiquement (PostgreSQL ne le fait pas, H2 si).
