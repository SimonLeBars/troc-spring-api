02 · JAVA MODERNE · TYPAGE STRICT

Un typage strict, et c'est une chance

exemples · fil rouge
// record : des données typées et immuables, sans code à écrire
public record Item(Long id, String name, int quantity, Long ownerId) { }
// enum : la liste fermée des statuts possibles
public enum TradeStatus { PROPOSED, ACCEPTED, EXECUTED }

String label = switch (trade.getStatus()) {     // switch exhaustif :
    case PROPOSED -> "en attente";              // oublier un statut,
    case ACCEPTED -> "validé";                  // et le code ne compile plus
    case EXECUTED -> "exécuté";
};

var items = itemService.findAll(ownerId);       // var : List<Item>, déduit ET vérifié
items.add("tomates");                           // ✗ refusé : une String n'est pas un Item
Le compilateur refuse le code incohérent avant l'exécution. En JavaScript, item.quantity = "dix" passerait sans broncher, et le bug se verrait en production.
10

Message : le typage fort n'est pas une contrainte bureaucratique, c'est un filet de sécurité. Dans un projet de plusieurs centaines de milliers de lignes maintenu par des équipes qui changent, c'est une raison majeure du choix de Java en entreprise.

Ce cours est l'occasion de prendre l'habitude d'un typage très cadré : records pour les données, enums pour les valeurs fermées, interfaces pour les contrats (partie 03).

Les records serviront dès la séance 2 (ItemProperties, ProposeTradeRequest). Un record est immuable : parfait pour une requête ou une configuration, à réfléchir pour une entité dont l'état change (le statut d'un Trade).

var ne rend pas Java dynamique : le type est déduit à la compilation et ne change plus.

02 · UN PEU D'HISTOIRE

Pourquoi Spring est né

Vingt ans plus tard, la même idée au centre : le conteneur IoC. Seule sa configuration a changé : XML, puis annotations, puis Boot.
11

Un EJB (Enterprise JavaBean) est un composant métier défini par la norme J2EE, déployé dans un serveur d'application (WebLogic, WebSphere, JBoss…) qui lui fournit transactions, sécurité, appels à distance. L'idée était bonne (le conteneur gère la technique, le développeur écrit le métier), c'est ce que fait Spring aujourd'hui. Le problème était le prix : un simple service = deux interfaces, une classe, un fichier XML, pour une seule méthode utile.

Côté client, pas d'injection : on allait chercher l'EJB soi-même dans un annuaire (JNDI). C'est exactement l'inverse de l'inversion de contrôle.

POJO = Plain Old Java Object : une classe Java normale, sans héritage ni interface imposés par un framework. Notre UserService en est un.

Java 5 (2004) apporte les annotations au langage : Spring commence en XML, les annotations arrivent avec Spring 2.5 (2007), Boot supprime la configuration répétitive en 2014. Depuis 2018, Java sort une version tous les six mois et une LTS (support long) tous les deux ans.

J2EE n'a pas disparu : devenu Jakarta EE, il fournit des standards (Servlet, Bean Validation…) que Spring utilise lui-même.

02 · SPRING ET SPRING BOOT

Un framework, un écosystème, et Boot par-dessus

12

Confusion fréquente : « Spring » et « Spring Boot » sont souvent employés l'un pour l'autre. Ce ne sont pas des concurrents, l'un est construit sur l'autre.

Spring Framework : le conteneur IoC (partie 04), plus des modules : AOP en séance 4, Web MVC pour nos contrôleurs, transactions en séance 3. Les projets de l'écosystème sont des bibliothèques séparées : dans le cours, Spring Data JDBC (séance 3) et Spring Security (TP 9).

Spring Boot n'ajoute presque aucun concept nouveau : il choisit des réglages par défaut raisonnables et branche tout automatiquement (« convention plutôt que configuration »). On le verra concrètement sur la structure du projet.

03 · SOLID

SOLID, et pourquoi le D nous intéresse

  • S — Single Responsibility une classe, une raison de changer
  • O — Open/Closed ouvert à l'extension, fermé à la modification
  • L — Liskov Substitution une sous-classe doit rester substituable
  • I — Interface Segregation préférer plusieurs interfaces ciblées
  • D — Dependency Inversion dépendre d'abstractions, pas d'implémentations
14

Survol rapide : une phrase par principe, pas d'exemple. Les autres reviendront au fil du cours (le S dès la diapo 16).

Le D est celui qui explique pourquoi Spring existe : c'est le fil de toute la séance.

Le couplage fort, et pourquoi il fait mal

UserService.java

  // le service choisit ET fabrique
  // sa dépendance
  private final InMemoryUserRepository users

  • Changer d'implémentationnouveau stockage = modifier chaque service qui fait new

03 · DEPENDENCY INVERSION

Inverser les dépendances : dépendre d'un contrat

Le service ne connaît plus que le contrat. Reste une question : qui lui fournit l'implémentation ? Réponse dans la partie 04.
17

Pointer le sens des flèches : avant, le haut dépend du bas. Après, le haut ET le bas dépendent de l'interface. C'est ça, « l'inversion ».

Lien avec la partie 02 : l'interface est un type, le compilateur vérifie que chaque implémentation respecte le contrat.

Laisser la question en suspens : elle est le point de départ de la partie 04.

À gauche, aucune annotation : c'est du Java pur. La dépendance est déclarée dans le constructeur, typée par l'interface. Changer de stockage (l'évolution 2 du TP) ne touche plus UserService. Pour l'évolution 1, il suffit de passer la même instance de repository à UserService et à ItemService, et les données redeviennent cohérentes.

À droite, le prix à payer : quelqu'un doit maintenant faire tous les new, dans un ordre imposé (pas de TradeService avant ses repositories). Sur un vrai projet, c'est ingérable à la main.

Transition : « et si on déléguait tout ce câblage à quelqu'un d'autre ? »

04 · INVERSION DE CONTRÔLE

Inversion de contrôle : le conteneur prend la main

« Ne nous appelez pas, c'est nous qui vous appellerons. »
Sans IoC, votre code crée ses objets. Avec IoC, le conteneur les crée, les assemble et appelle votre code. L'injection de dépendances est la façon de faire de l'IoC qu'on utilise ici.
21

Principe d'Hollywood : l'acteur ne harcèle pas le studio, il laisse son CV et attend l'appel. Votre classe déclare ce dont elle a besoin et attend que Spring l'appelle.

Deux analogies, deux idées : la prise explique la DI (dépendre d'une norme), Hollywood explique l'IoC (qui a la main sur le cycle de vie).

L'ApplicationContext est le conteneur qui détient tous les beans. Spring résout l'ordre tout seul : il crée d'abord ce dont les autres ont besoin. Si une dépendance est introuvable, l'application refuse de démarrer, avec un message explicite.

Vocabulaire : un « bean » est simplement un objet dont Spring s'occupe (création, assemblage). La diapo suivante montre comment on dit à Spring « cette classe est un bean ».

04 · ANNOTATIONS

Déclarer ses beans : quelques annotations

TrocApplication.java · UserService.java · InMemoryUserRepository.java
@SpringBootApplication                     // point d'entrée : démarre le conteneur
public class TrocApplication { ... }

@Service                                   // bean de la couche métier
public class UserService {
    private final UserRepository users;
    public UserService(UserRepository users) {  // injecté par Spring,
        this.users = users;                    // en lui passant le bean
    }
}

@Repository                                // bean d'accès aux données
public class InMemoryUserRepository implements UserRepository { ... }
@Service, @Repository, @RestController : des @Component spécialisés, un par couche.
22

Le UserService est le même que sur la diapo 20, avec une seule annotation en plus. Tout le reste est fait par le conteneur.

Aucune annotation à ajouter sur le constructeur : quand une classe n'a qu'un seul constructeur, Spring l'utilise automatiquement pour injecter les dépendances.

@RestController servira pour UserController, avec @GetMapping et @PostMapping sur ses méthodes : c'est l'objectif du TP (détails et syntaxes dans le support).

04 · START.SPRING.IO OU INTELLIJ · MAVEN · JAVA 25 · SPRING BOOT 4.1

Structure d'un projet Spring Boot

troc-api/
troc-api/
├── pom.xml                                   ← un starter : Spring Web
└── src/
    ├── main/java/fr/cours/troc/
    │   ├── TrocApplication.java              ← @SpringBootApplication
    │   ├── user/                             ← une fonctionnalité = un package
    │   │   ├── User.java
    │   │   ├── UserController.java           ← les couches restent visibles
    │   │   ├── UserService.java                dans les noms de classes
    │   │   ├── UserRepository.java
    │   │   └── InMemoryUserRepository.java
    │   ├── item/                             ← ItemService (évolution 1)
    │   └── trade/                            ← séance 2
    ├── main/resources/application.properties ← configuration (séance 2)
    └── test/java/fr/cours/troc/              ← tests (séance 4)
Boot fait le reste : auto-configuration, Tomcat embarqué. Le scan part du package de TrocApplication : user, item, trade en dessous.
23

start.spring.io et l'assistant IntelliJ génèrent le même projet. Une seule dépendance pour aujourd'hui : Spring Web. Les étapes détaillées sont dans le support de TP.

Ce que Boot ajoute : un starter tire toutes les bibliothèques nécessaires en versions compatibles ; l'auto-configuration regarde ce qui est présent (Spring Web ? alors serveur + JSON) et crée les beans en conséquence ; Tomcat est inclus, rien à installer ; on obtient un JAR exécutable. Ce n'est pas magique, et on peut toujours remplacer un bean auto-configuré par le sien.

Piège classique : une classe annotée placée hors du package racine n'est pas détectée.

Découpage par fonctionnalité plutôt que par couche : tout ce qui concerne les utilisateurs est au même endroit, les dépendances entre fonctionnalités se voient (trade dépendra de user et item), et chaque membre du groupe peut prendre une fonctionnalité. L'autre découpage (controller/, service/, repository/) fonctionne aussi ; les couches de la diapo 15 restent là, ce sont des rôles de classes, pas forcément des dossiers.
