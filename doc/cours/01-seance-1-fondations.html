THÉORIE A · SOLID

SOLID, et pourquoi le D nous intéresse

  • S — Single Responsibility une classe, une raison de changer
  • O — Open/Closed ouvert à l'extension, fermé à la modification
  • L — Liskov Substitution une sous-classe doit rester substituable
  • I — Interface Segregation préférer plusieurs interfaces ciblées
  • D — Dependency Inversion dépendre d'abstractions, pas d'implémentations
09

Survol rapide : une phrase par principe, pas d'exemple. Les autres reviendront au fil du cours (le S dès la diapo 12).

Le D est celui qui explique pourquoi Spring existe : c'est le fil de toute la séance.

THÉORIE A · COUPLAGE FORT

Le couplage fort dans le code

UserService.java
public class UserService {

    // le service choisit ET fabrique sa dépendance
    private final InMemoryUserRepository users = new InMemoryUserRepository();

    public List<User> findAll() {
        return users.findAll();
    }

    public User create(User user) {
        return users.save(user);
    }
}
11

Code volontairement naïf, c'est ce que tout le monde écrit spontanément. Demander à la salle : « qu'est-ce qui vous gêne ici ? » avant de passer à la diapo suivante.

THÉORIE A · COUPLAGE FORT

Pourquoi ça fait mal

  • Données incohérentes deux services, deux new : deux stockages qui s'ignorent
  • Changer d'implémentation nouveau stockage = modifier chaque service qui fait new
  • Effet cascade le constructeur du repository change ? Plus rien ne compile
  • Deux métiers dans une classe il gère les utilisateurs ET fabrique ses outils (le S de SOLID)
12

Si la salle a trouvé ces points à la diapo précédente, les valider plutôt que les dérouler.

Ne pas encore donner la solution en code : ils vont vivre ces trois problèmes dans le TP bloc 1, via les évolutions demandées par le client.

Un quatrième problème existe (impossible de tester UserService seul, sans son vrai stockage) : ne pas le développer, on y reviendra en séance 4.

THÉORIE A · DEPENDENCY INVERSION

Inverser les dépendances : dépendre d'un contrat

Le service ne connaît plus que le contrat. Reste une question : qui lui fournit l'implémentation ? Réponse après le TP.

Pointer le sens des flèches : avant, le haut dépend du bas. Après, le haut ET le bas dépendent de l'interface. C'est ça, « l'inversion ».

THÉORIE B · INVERSION DE CONTRÔLE

Inversion de contrôle

« Ne nous appelez pas, c'est nous qui vous appellerons. »
SANS IOC
Votre code crée ses objets et décide quand les appeler.
AVEC IOC
Le conteneur crée les objets, les assemble et appelle votre code au bon moment.
DI ≠ IOC
L'injection de dépendances est une façon de faire de l'IoC : les dépendances arrivent de l'extérieur.
19

Principe d'Hollywood : l'acteur ne harcèle pas le studio, il laisse son CV et attend l'appel. Votre classe déclare ce dont elle a besoin et attend que Spring l'appelle.

Deux analogies, deux idées : la prise explique la DI (dépendre d'une norme), Hollywood explique l'IoC (qui a la main sur le cycle de vie).

THÉORIE B · ANNOTATIONS

Déclarer ses beans : quelques annotations

TrocApplication.java · UserService.java · InMemoryUserRepository.java
@SpringBootApplication                     // point d'entrée : démarre le conteneur
public class TrocApplication { ... }

@Service                                   // bean de la couche métier
public class UserService {
    private final UserRepository users;
    public UserService(UserRepository users) {  // injecté par Spring,
        this.users = users;                    // en lui passant le bean
    }
}

@Repository                                // bean d'accès aux données
public class InMemoryUserRepository implements UserRepository { ... }
@Service, @Repository, @RestController : des @Component spécialisés, un par couche.
20

Le UserService est le même que sur la diapo avant/après, avec une seule annotation en plus. Tout le reste est fait par le conteneur.

Vocabulaire à poser ici : un « bean » est simplement un objet dont Spring s'occupe (création, assemblage). Les annotations servent à dire à Spring « cette classe est un bean ».

Aucune annotation à ajouter sur le constructeur : quand une classe n'a qu'un seul constructeur, Spring l'utilise automatiquement pour injecter les dépendances.

Transition : ces annotations sont des étiquettes. La diapo suivante montre comment Spring les trouve et s'en sert au démarrage.

THÉORIE B · LE CONTENEUR

L'ApplicationContext au démarrage

21

Étape 1 : le scan cherche les classes portant les annotations de la diapo précédente (@Service, @Repository, @RestController…).

L'ApplicationContext est le conteneur qui détient tous les beans.

Spring résout l'ordre tout seul : il crée d'abord ce dont les autres ont besoin. Si une dépendance est introuvable, l'application refuse de démarrer, avec un message explicite.

Le scan part du package de TrocApplication : user, item, trade doivent être en dessous.
22

start.spring.io et l'assistant IntelliJ génèrent le même projet. Une seule dépendance pour aujourd'hui : Spring Web. Les étapes détaillées sont dans le support de TP.

Piège classique : une classe annotée placée hors du package racine n'est pas détectée. Nom du package à adapter au choix du groupe.

Découpage par fonctionnalité plutôt que par couche : tout ce qui concerne les utilisateurs est au même endroit, les dépendances entre fonctionnalités se voient (trade dépendra de user et item), et chaque membre du groupe peut prendre une fonctionnalité.

Vous croiserez souvent l'autre découpage dans les tutos (controller/, service/, repository/) : il fonctionne aussi, mais disperse une même fonctionnalité dans trois dossiers. Les couches du schéma de la diapo 10 restent là : ce sont des rôles de classes, pas forcément des dossiers.

THÉORIE B · OBJECTIF DE FIN DE SÉANCE

Votre objectif : une API qui répond

UserController.java
@RestController                                // bean de la couche web, répond en JSON
public class UserController {

    private final UserService userService;

    public UserController(UserService userService) {
        this.userService = userService;
    }

    @GetMapping("/users")                        // GET /users
    public List<User> findAll() { return userService.findAll(); }

    @PostMapping("/users")                       // POST /users + corps JSON
    public User create(@RequestBody User user) { return userService.create(user); }
}
On retrouve les deux requêtes du début de séance : GET /users liste, POST /users crée.
23

Objectif obligatoire pour tous les groupes avant la fin de séance : le refactor IoC du bloc 1, puis ces deux endpoints.

Après le refactor, faire refaire l'évolution 2 et recompter les fichiers modifiés : un seul avec l'injection manuelle, et avec Spring il suffit de déplacer @Repository. Comparer avec les chiffres relevés au checkpoint #1.

Revenir sur la diapo « Une API REST, concrètement » : c'est exactement ce qu'on vient de coder. Spring convertit l'objet Java en JSON (et le JSON reçu en objet Java avec @RequestBody).

Par défaut, le POST renvoie 200 et non 201 : les codes de statut seront traités en séance 2. Spring Boot embarque son propre serveur web, on lance le main et l'API écoute sur le port 8080.
