Le serveur ne croit plus le client sur parole : il a lui-même signé le jeton qui dit qui appelle.
03

Le 403 « tu n'es pas le destinataire » de la séance 3 existe déjà, mais il ne protège rien : il suffit de mentir sur userId. La règle métier est bonne, c'est l'information d'entrée qui n'est pas fiable.

Mallory est le prénom traditionnel de l'attaquant dans les exemples de sécurité (Alice et Bob communiquent, Mallory s'interpose).

PARTIE 01 · VOCABULAIRE

Deux questions, deux codes HTTP

  • Authentification qui es-tu ? on le prouve : mot de passe, puis jeton
  • Autorisation as-tu le droit ? se décide une fois l'identité connue
  • Jeton (JWT) preuve d'identité signée par le serveur, qui expire
  • Rôle ROLE_USER, ROLE_ADMIN : des droits attribués à un compte
  • 401 Unauthorized pas authentifié : jeton absent, invalide ou expiré
  • 403 Forbidden authentifié, mais pas autorisé à faire ça
04

Toujours dans cet ordre : on ne peut pas décider de ce qu'une personne a le droit de faire tant qu'on ne sait pas qui elle est.

Piège de vocabulaire : 401 s'appelle « Unauthorized » mais signifie « non authentifié ». C'est une erreur historique de la norme HTTP. Retenir : 401 = je ne sais pas qui tu es, 403 = je sais qui tu es, et c'est non.

JWT = JSON Web Token, prononcé « jot ». Bearer = « porteur » : celui qui présente le jeton est considéré comme son titulaire, d'où l'importance de ne pas le laisser fuiter.

PARTIE 02 · LE MÉCANISME

Le mot de passe une fois, le jeton ensuite

La base et BCrypt ne servent qu'au login. Ensuite, le serveur vérifie une signature : c'est rapide et il ne garde rien en mémoire.
06

Temps 1 : le seul moment où le mot de passe circule. AuthenticationManager charge le compte (UserDetailsService, notre code) et compare le mot de passe au haché (PasswordEncoder). Succès : TokenService fabrique un jeton, JwtEncoder le signe avec une clé que seul le serveur connaît. Échec : 401.

Temps 2 : un filtre (BearerTokenAuthenticationFilter) lit l'en-tête Authorization: Bearer, JwtDecoder vérifie la signature et la date d'expiration. Si tout va bien, le contenu du jeton est rangé dans le SecurityContext ; le contrôleur le récupère avec @AuthenticationPrincipal. Puis AuthorizationFilter applique les règles de SecurityConfig : refus → 403.

Un filtre (Servlet Filter) s'exécute avant le DispatcherServlet de Spring MVC, donc avant tout contrôleur. Spring Security en installe une quinzaine ; seuls ceux qui nous concernent sont dessinés.

Encore de l'IoC : on ne réécrit pas la chaîne, on fournit des beans (UserDetailsService, PasswordEncoder, JwtEncoder, JwtDecoder, SecurityFilterChain) que Spring branche aux bons endroits.

HMAC-SHA256(en-tête.contenu, clé)
Encodé, pas chiffré : tout le monde peut le lire. Modifier un seul caractère casse la signature : 401.
07

Ce jeton est réel : signé avec la clé de dev du support (diapo 15). Le coller dans un décodeur JWT en ligne permet de vérifier son contenu et sa signature. Bonne démonstration en direct.

Pourquoi Mallory ne peut pas fabriquer un jeton « sub: 2 » : la signature est calculée avec une clé secrète que seul le serveur connaît. Elle peut changer le contenu, mais pas recalculer une signature valide.

Conséquence : ne jamais mettre dans un jeton une information qui ne doit pas être lue (mot de passe, données personnelles). Le jeton est une carte d'identité, pas un coffre-fort.

iat (issued at) et exp (expiration) sont des secondes depuis le 1er janvier 1970. Ici, émis le 22 octobre 2026 à 12h, valable une heure.

@Table("users")
public class User {
    @Id private Long id;
    private String name;
    private String username;
    private String passwordHash; // password_hash
    private String role;         // USER, ADMIN
}

public interface UserRepository

UNIQUE : deux comptes ne peuvent pas partager un identifiant, et l'index créé avec accélère chaque login.
11

name reste le nom affiché (« Alice Martin »), username est l'identifiant de connexion (« alice »). On pourrait fusionner les deux ; les séparer évite de casser les données existantes.

Rappel séance 3 : à cause de IF NOT EXISTS, modifier le CREATE ne change pas une table existante. Supprimer le dossier data/ et redémarrer.

Critère de notation « concepts SQL, index » : la contrainte UNIQUE crée un index, et findByUsername est appelé à chaque login. C'est un index qui se justifie très bien à l'oral.

VARCHAR(100) pour le haché : un haché BCrypt fait 60 caractères, plus le préfixe {bcrypt} (8). On garde de la marge si l'algorithme change.

PARTIE 03 · ÉTAPE 2

UserDetailsService : le pont entre Spring et votre table

src/main/java/fr/cours/troc/security/TrocUserDetailsService.java
@Service
public class TrocUserDetailsService implements UserDetailsService {

    private final UserRepository users;   // injecté par le constructeur

    @Override
    public UserDetails loadUserByUsername(String username) {
        User user = users.findByUsername(username)
            .orElseThrow(() -> new UsernameNotFoundException(username));
        return org.springframework.security.core.userdetails.User
            .withUsername(user.getUsername())
            .password(user.getPasswordHash())   // le haché, jamais le mot de passe
            .roles(user.getRole())
            .build();
    }
}
Appelé uniquement au login. Spring compare ensuite lui-même le mot de passe reçu au haché.
12

Encore l'IoC de la séance 1 : on fournit une implémentation d'interface, le framework l'utilise. Le compte « user » généré au démarrage disparaît.

Collision de noms : notre entité s'appelle User, et Spring Security a aussi une classe User (un builder de UserDetails). D'où le nom complet.

UsernameNotFoundException et mauvais mot de passe produisent la même erreur (401) : Spring ne dit volontairement pas lequel des deux était faux, pour qu'un attaquant ne puisse pas tester quels identifiants existent.

PARTIE 03 · ÉTAPE 3

On ne stocke jamais un mot de passe, seulement son haché

EN BASE · CE QU'ON DOIT Y TROUVER
SELECT username, password_hash FROM users
alice | potager123          -- jamais

alice | {bcrypt}$2a$10$Xq0S…k7Gm
         │      │   │
         │      │   └ sel + haché
         │      └ coût : 2^10 tours
         └ algorithme utilisé
DANS LE CODE · L'ENCODEUR ET LE VÉRIFICATEUR
security/SecurityConfig.java
@Bean
PasswordEncoder passwordEncoder() {
    return PasswordEncoderFactories
        .createDelegatingPasswordEncoder();
}

@Bean   // utilisé par POST /auth/token
AuthenticationManager authenticationManager(
        UserDetailsService uds,
        PasswordEncoder encoder) {
    var provider = new DaoAuthenticationProvider(uds);
    provider.setPasswordEncoder(encoder);
    return new ProviderManager(provider);
}
Hacher n'est pas chiffrer : impossible de retrouver le mot de passe, on vérifie qu'un essai donne le même haché.
13

Pourquoi : si la base fuit (sauvegarde perdue, injection SQL), les mots de passe ne doivent pas être lisibles. Les gens réutilisent les mêmes partout.

Le sel : une valeur aléatoire mélangée au mot de passe avant hachage, stockée dans le résultat. Deux utilisateurs avec le même mot de passe ont deux hachés différents.

Le coût : BCrypt est volontairement lent (2^10 = 1024 tours, de l'ordre de 100 ms). Imperceptible pour un login, très pénalisant pour un attaquant qui teste des milliards de combinaisons. C'est aussi pourquoi on ne veut pas le faire tourner à chaque requête : avec un jeton, il ne tourne qu'au login.

AuthenticationManager : c'est lui qui enchaîne UserDetailsService puis PasswordEncoder. On le déclare explicitement pour pouvoir l'appeler depuis AuthController (diapo 17). Spring Security 7 exige le UserDetailsService dans le constructeur de DaoAuthenticationProvider.

Le préfixe {bcrypt} : le « delegating » encoder sait lire plusieurs algorithmes, et un changement d'algorithme futur reste compatible avec les anciens hachés. Erreur classique : insérer en base un haché sans préfixe → « There is no PasswordEncoder mapped for the id null ».

PARTIE 03 · ÉTAPE 3 · INSCRIPTION

POST /users devient l'inscription

user/RegisterRequest.java · user/UserResponse.java · user/UserService.java
public record RegisterRequest(String name, String username, String password) { }
public record UserResponse(Long id, String name, String username) { }   // pas de haché !

@Service
public class UserService {
    // UserRepository users, PasswordEncoder passwordEncoder : injectés par le constructeur

    public UserResponse register(RegisterRequest request) {
        if (users.findByUsername(request.username()).isPresent()) {
            throw new ResponseStatusException(HttpStatus.CONFLICT, "username déjà pris");
        }
        String hash = passwordEncoder.encode(request.password());
        User saved = users.save(new User(request.name(), request.username(), hash, "USER"));
        return new UserResponse(saved.getId(), saved.getName(), saved.getUsername());
    }
}
Le client choisit son mot de passe, pas son rôle. Et la réponse JSON ne renvoie jamais le haché.
14

Requête ≠ entité, comme en séance 2 : sans UserResponse, GET /users renverrait password_hash de tout le monde en JSON. C'est la fuite la plus fréquente dans les projets étudiants.

Le rôle est fixé par le serveur. Si RegisterRequest contenait un champ role, n'importe qui pourrait s'inscrire ADMIN.

Le 409 n'est qu'une première vérification : deux inscriptions simultanées du même username passeraient toutes les deux le if. C'est la contrainte UNIQUE qui tranche (DuplicateKeyException). « Le code vérifie, la base garantit », séance 3.

Une clé secrète pour signer et vérifier

LE SECRET · EXTERNALISÉ (SÉANCE 2)

# application-dev.properties
troc.jwt.secret=dev-secret-de-32-caracteres-min!!

@ConfigurationProperties("troc.jwt")
public record JwtProperties(
    String secret,
    Duration ttl
) { }
LES BEANS · ENCODEUR ET DÉCODEUR
security/JwtConfig.java
@Configuration
public class JwtConfig {
  @Bean
  SecretKey jwtKey(JwtProperties props) {
    byte[] k = props.secret().getBytes(UTF_8);
    return new SecretKeySpec(k, "HmacSHA256");
  }
  @Bean
  JwtEncoder jwtEncoder(SecretKey key) {
    return NimbusJwtEncoder.withSecretKey(key).build();
  }
  @Bean
  JwtDecoder jwtDecoder(SecretKey key) {
    return NimbusJwtDecoder.withSecretKey(key).build();
  }
}
Qui connaît la clé peut fabriquer des jetons pour n'importe qui : elle vient de l'environnement, jamais de git.
15

HS256 (HMAC) : la même clé signe et vérifie. Simple, et suffisant quand c'est la même application qui émet et vérifie les jetons. Si plusieurs services devaient vérifier les jetons, on passerait à une paire de clés RSA : clé privée pour signer, clé publique partagée pour vérifier.

Taille minimale : 256 bits, soit 32 octets pour HS256. Avec un secret trop court, la signature échoue au premier login (« The secret length must be at least 256 bits »). En production, générer un secret aléatoire : openssl rand -base64 48.

Rappel séance 2 : la variable d'environnement TROC_JWT_SECRET l'emporte sur le fichier ; le profil dev fournit un secret de développement pour que l'appli démarre sans configuration. Sans profil dev et sans variable, l'appli ne démarre pas : c'est voulu.

Changer le secret invalide tous les jetons en circulation : c'est le seul « bouton de déconnexion générale ».

Imports : UTF_8 en import statique depuis StandardCharsets ; SecretKeySpec depuis javax.crypto.spec (c'est bien javax, qui fait partie du JDK, pas de Jakarta EE).

PARTIE 03 · ÉTAPE 5

TokenService : fabriquer et signer un jeton

src/main/java/fr/cours/troc/security/TokenService.java
@Service
public class TokenService {
    // JwtEncoder encoder, JwtProperties props : injectés par le constructeur

    public String issue(User user) {
        Instant now = Instant.now();
        JwtClaimsSet claims = JwtClaimsSet.builder()
            .issuer("troc-api")
            .subject(String.valueOf(user.getId()))      // qui : l'id, signé donc fiable
            .claim("username", user.getUsername())
            .claim("roles", List.of(user.getRole()))
            .issuedAt(now)
            .expiresAt(now.plus(props.ttl()))           // 1 h, puis 401
            .build();
        JwsHeader header = JwsHeader.with(MacAlgorithm.HS256).build();
        return encoder.encode(JwtEncoderParameters.from(header, claims)).getTokenValue();
    }
}
Le contenu de la diapo 07, écrit en Java. L'en-tête HS256 doit correspondre au type de clé.
16

sub (subject) contient l'id de l'utilisateur : c'est lui que les contrôleurs liront à la place de proposerId. Comme il est signé, impossible de le remplacer par l'id de Bob.

Durée de vie courte : un jeton volé reste valable jusqu'à son expiration, on ne peut pas le révoquer. Une heure est un compromis raisonnable pour le projet. Les applications réelles ajoutent un « refresh token » pour en obtenir un nouveau sans redemander le mot de passe : piste de bonus avancée.

Le rôle est copié dans le jeton : si un admin change le rôle d'un utilisateur, le changement ne s'applique qu'au prochain login. Encore une conséquence de « le serveur ne garde rien ».

JwsHeader explicite : par défaut, l'encodeur s'attend à une signature RSA. Sans cet en-tête, l'encodage échoue avec une clé HMAC.

PARTIE 03 · ÉTAPE 5

POST /auth/token : le seul endroit où passe le mot de passe

security/LoginRequest.java · security/TokenResponse.java · security/AuthController.java
public record LoginRequest(String username, String password) { }
public record TokenResponse(String token, long expiresIn) { }

@RestController
public class AuthController {
    // AuthenticationManager authManager, UserRepository users, TokenService tokens

    @PostMapping("/auth/token")
    public TokenResponse token(@RequestBody LoginRequest request) {
        try {
            authManager.authenticate(UsernamePasswordAuthenticationToken
                .unauthenticated(request.username(), request.password()));
        } catch (AuthenticationException e) {
            throw new ResponseStatusException(HttpStatus.UNAUTHORIZED, "identifiants invalides");
        }
        User user = users.findByUsername(request.username()).orElseThrow();
        return new TokenResponse(tokens.issue(user), tokens.ttlSeconds());
    }
}
authenticate() appelle UserDetailsService puis BCrypt. Échec : 401. Succès : un jeton.
17

Login en JSON plutôt qu'en HTTP Basic : c'est ce qu'enverra un front Angular depuis un formulaire, et le mot de passe n'apparaît pas dans un en-tête qui pourrait être journalisé.

ttlSeconds() : une petite méthode de TokenService qui renvoie props.ttl().toSeconds(), pour que le client sache quand redemander un jeton.

Le message d'erreur reste vague (« identifiants invalides ») : ne jamais dire si c'est l'identifiant ou le mot de passe qui est faux.

Bonus sécurité : limiter le nombre d'essais par identifiant (compteur d'échecs, blocage temporaire) contre les attaques par force brute.

PARTIE 03 · ÉTAPE 6

SecurityConfig : un jeton exigé partout, sauf deux routes

src/main/java/fr/cours/troc/security/SecurityConfig.java
@Configuration
public class SecurityConfig {
    @Bean
    SecurityFilterChain securityFilterChain(HttpSecurity http) throws Exception {
        http
            .authorizeHttpRequests(auth -> auth
                .requestMatchers(HttpMethod.POST, "/users", "/auth/token").permitAll()
                .requestMatchers("/h2-console/**").permitAll()            // dev uniquement
                .anyRequest().authenticated())
            .oauth2ResourceServer(rs -> rs.jwt(Customizer.withDefaults())) // Bearer exigé
            .csrf(csrf -> csrf.disable())                                // pas de cookie
            .sessionManagement(s -> s.sessionCreationPolicy(STATELESS))
            .headers(h -> h.frameOptions(f -> f.sameOrigin()));         // console H2
        return http.build();
    }
    // + les beans PasswordEncoder et AuthenticationManager (diapo 13)
}
Les règles se lisent de haut en bas : la première qui correspond gagne. anyRequest() toujours en dernier.
18

oauth2ResourceServer + jwt : active le filtre qui lit « Authorization: Bearer … » et le JwtDecoder de la diapo 15. Le vocabulaire OAuth2 vient de la norme qui a popularisé ces jetons ; on n'utilise ici qu'une petite partie (« resource server » = une API qui accepte des jetons).

Pas de httpBasic ni de formLogin : le seul moyen d'être authentifié est un jeton valide. Pas besoin de @EnableWebSecurity avec Spring Boot.

CSRF : protection contre un site malveillant qui ferait envoyer une requête par le navigateur de la victime, en profitant de son cookie. Le jeton n'est pas un cookie : le navigateur ne l'envoie pas tout seul, la protection n'a pas d'objet. STATELESS : Spring ne crée pas de session HTTP.

La console H2 ne doit pas être ouverte en production : idéalement, cette ligne n'existe que dans le profil dev (séance 2). Imports : HttpMethod (org.springframework.http), SessionCreationPolicy.STATELESS en import statique.

APRÈS · LE JETON SIGNÉ
trade/TradeController.java
public record ProposeTradeRequest(
    Long offeredItemId, int offeredQuantity,
    Long recipientId,
    Long requestedItemId, int requestedQuantity
) { }

@PostMapping("/{id}/accept")
public Trade accept(@PathVariable Long id,
    @AuthenticationPrincipal Jwt jwt) {
  Long myId = Long.valueOf(jwt.getSubject());
  return tradeService.accept(id, myId);
}
TradeService ne change pas : il reçoit toujours un identifiant. Mais le 403 « pas le destinataire » devient enfin fiable.
19

@AuthenticationPrincipal : Spring lit le SecurityContext (diapo 06) et injecte le jeton décodé en paramètre, comme il injecte un @PathVariable. Jwt vient de org.springframework.security.oauth2.jwt.

Aucune requête en base pour savoir qui appelle : l'id est dans le jeton, et la signature garantit qu'il n'a pas été modifié.

L'architecture en couches paie : seule la couche contrôleur change. Le service et ses tests unitaires (séance 4) restent identiques. La règle métier « seul le destinataire accepte » reste dans le service.

Même traitement pour propose (proposerId), reject, et GET /trades?userId= qu'on peut remplacer par GET /trades/mine. Mettre à jour les fichiers de requêtes de test.

# 3. sans jeton                                                        → 401
curl -i localhost:8080/items
# 4. avec le jeton                                                     → 200 OK
curl -i -H "Authorization: Bearer $TOKEN" localhost:8080/items
# 5. accepter un troc destiné à Bob                                    → 403
curl -i -H "Authorization: Bearer $TOKEN" -X POST localhost:8080/trades/7/accept
Une heure plus tard, la requête 4 répond 401 : le jeton a expiré, il faut repasser par l'étape 2.
20

Client HTTP d'IntelliJ (fichiers .http) : après la requête de login, ajouter le gestionnaire « > {% client.global.set("token", response.body.token); %} », puis écrire « Authorization: Bearer {{token}} » dans les requêtes suivantes. Le jeton est récupéré automatiquement.

En réponse à un 401, l'en-tête WWW-Authenticate: Bearer donne la raison (jeton absent, invalid_token, expiré) : premier réflexe de débogage.

Le 401 et le 403 ne viennent pas du même endroit : le 401 de la chaîne de filtres (diapo 06), le 403 de la requête 5 du service de troc (règle métier). Les deux sont des réponses correctes.

En production, HTTPS reste indispensable : le mot de passe au login et le jeton ensuite doivent voyager chiffrés.

PARTIE 04 · AUTORISATION

Les rôles voyagent dans le jeton

application.properties · SecurityConfig.java · UserService.java
# où lire les rôles dans le jeton : claim "roles", préfixe ROLE_ ("ADMIN" → ROLE_ADMIN)
spring.security.oauth2.resourceserver.jwt.authorities-claim-name=roles
spring.security.oauth2.resourceserver.jwt.authority-prefix=ROLE_

// règle par URL, dans SecurityConfig
.requestMatchers(HttpMethod.DELETE, "/users/**").hasRole("ADMIN")

// ou règle par méthode : @EnableMethodSecurity sur SecurityConfig, puis
@PreAuthorize("hasRole('ADMIN')")
public void delete(Long id) { ... }
Un rôle dit qui a le droit en général. « Seul le destinataire accepte ce troc-là » dépend des données : règle métier, dans le service.
22

Sans ces deux propriétés, Spring cherche les droits dans un claim « scope » et les préfixe par SCOPE_ : hasRole("ADMIN") échoue alors toujours, avec un 403 difficile à comprendre.

@PreAuthorize repose sur l'AOP de la séance 4 : Spring entoure le bean d'un proxy qui vérifie la règle avant d'appeler la méthode. Mêmes limites que @Transactional : un appel interne (this.delete()) contourne la vérification.

Créer un admin : pas par l'API (le rôle n'est jamais choisi par le client). Un UPDATE users SET role = 'ADMIN' dans la console H2, puis se reconnecter pour obtenir un jeton avec le nouveau rôle.

Choix à justifier en présentation : règles par URL (vue d'ensemble) ou par méthode (au plus près du métier). Les deux se défendent ; éviter de mélanger sans raison.

jwt() fournit un jeton déjà validé. Boot 4 : dépendance de test spring-boot-starter-security-test.
23

Effet immédiat de la sécurité : les tests d'intégration MockMvc de la séance 4 répondent 401. Correction : ajouter .with(jwt().jwt(j -> j.subject("…"))) aux requêtes. Les tests unitaires du service, eux, ne bougent pas : pas de Spring, pas de sécurité.

jwt() vient de SecurityMockMvcRequestPostProcessors (import statique). Il place directement un jeton décodé dans le SecurityContext, sans signature : on choisit le sub, et donc l'utilisateur, test par test. Pour les rôles : .authorities(new SimpleGrantedAuthority("ROLE_ADMIN")).

@WithMockUser, qu'on croise dans beaucoup de tutos, ne convient pas ici : il ne fournit pas un Jwt, et @AuthenticationPrincipal Jwt recevrait null.

Bon test d'intégration complet en bonus : inscription, POST /auth/token, extraction du jeton de la réponse, puis requête avec « Authorization: Bearer ». Il traverse le vrai encodeur et le vrai décodeur.

Ne pas désactiver la sécurité dans les tests « pour que ça passe » : le 401 et le 403 font partie du contrat de l'API, ils méritent leurs tests.

PARTIE 04 · CHOISIR

Pourquoi un jeton plutôt que Basic ou une session ?

Un bon sujet pour l'oral : pourquoi pas Basic ? Le mot de passe et BCrypt ne servent qu'une fois, le reste est signé et expire.
24

HTTP Basic : le plus simple à mettre en place, mais le mot de passe voyage dans chaque requête (en Base64, donc lisible sans HTTPS) et risque de finir dans des journaux, des proxys, l'historique du terminal. Le client doit le conserver ; aucune expiration, aucune déconnexion. Et BCrypt, lent exprès, tourne à chaque appel : un attaquant peut s'en servir pour saturer le serveur.

Session : le modèle classique des sites web. Le cookie part automatiquement avec chaque requête du navigateur, d'où le besoin de la protection CSRF. Le serveur garde un état, ce qui complique le passage à plusieurs instances.

JWT : le serveur ne garde rien et vérifie une signature. Limite principale : un jeton volé reste valable jusqu'à expiration. Parades : durée courte, HTTPS, ne jamais le journaliser, et un refresh token pour les applications réelles.

Pour aller plus loin : déléguer complètement l'authentification à un serveur d'autorisation (Keycloak, ou Spring Authorization Server, intégré à Spring Security 7). L'API ne fait alors que vérifier les jetons, exactement comme ici.

PARTIE 04 · PIÈGES COURANTS

Ça ne marche pas : les suspects habituels

  • 401 partout normal : tout est fermé, même GET /users
  • 401 avec un jeton expiré, mal copié, ou « Bearer » oublié
  • 403 sur chaque POST CSRF encore actif : csrf.disable() oublié
  • Erreur au login secret de moins de 32 caractères : trop court pour HS256
  • hasRole toujours refusé propriétés authorities-claim-name oubliées
  • Tuto avec .and() Spring Security 5 ou 6 : en 7, lambdas uniquement
25

Pour comprendre une décision de sécurité : logging.level.org.springframework.security=DEBUG dans application.properties affiche chaque filtre traversé et la raison d'un refus. Lire aussi l'en-tête WWW-Authenticate des réponses 401.

Autres pièges : console H2 blanche (frameOptions sameOrigin manquant) ; « There is no PasswordEncoder mapped for the id null » (haché inséré en base sans préfixe {bcrypt}) ; tests de la séance 4 en 401 (ajouter .with(jwt())).

Tutoriels anciens, ce qui ne compile plus en Spring Security 7 : WebSecurityConfigurerAdapter (supprimé dès la version 6), authorizeRequests() (remplacé par authorizeHttpRequests), antMatchers et mvcMatchers (remplacés par requestMatchers), le chaînage .and(). Beaucoup de tutos JWT utilisent aussi une bibliothèque externe (jjwt) et un filtre écrit à la main : inutile, Spring Security sait vérifier les jetons lui-même.
