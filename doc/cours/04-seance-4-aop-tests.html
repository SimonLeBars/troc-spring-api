Le log noyé dans le métier, ou mis à part

AVANT · LOG MÉLANGÉ AU MÉTIER

Principe S de SOLID : une classe, une seule raison de changer. Changer le format du log ne doit pas toucher au troc.
06

À gauche : 7 lignes sur 13 ne parlent pas de troc. Et il faudrait les recopier dans chaque méthode de chaque service. Un oubli, et une opération n'est plus tracée.

Lien séance 1 : le principe S (responsabilité unique). TradeService change si les règles du troc changent, pas si l'équipe exploitation veut un autre format de log.

Le log reste en SLF4J (Logger, LoggerFactory), fourni par Spring Boot : pas de System.out.println.

AOP · VOCABULAIRE

Quatre mots, une phrase

  • Join point un endroit interceptable : chez Spring, l'appel d'une méthode d'un bean
  • Pointcut le filtre qui choisit les join points : « les méthodes de TradeService »
  • Advice le code à exécuter, et quand : avant, après, en cas d'erreur, autour
  • Aspect la classe qui regroupe pointcuts et advices
  • En une phrase « avant (advice) chaque méthode de TradeService (pointcut), écrire une ligne de log »
07

Les termes anglais sont gardés : ce sont ceux de la documentation et des annotations. Join point se traduit parfois « point de jonction », advice « greffon ».

Le plus utile à retenir : pointcut = où, advice = quoi et quand.

AOP · DANS LE CODE

Un aspect, c'est une classe annotée

trade/TradeLoggingAspect.java
@Aspect                                            // je contiens des advices
@Component                                         // un bean, comme les autres
public class TradeLoggingAspect {
    private static final Logger log = LoggerFactory.getLogger(TradeLoggingAspect.class);

    @Pointcut("execution(* fr.cours.troc.trade.TradeService.*(..))")
    void tradeOperations() {}                       // un nom pour le filtre

    @Before("tradeOperations()")
    public void logAttempt(JoinPoint jp) {
        log.info("→ {} {}", jp.getSignature().getName(), Arrays.toString(jp.getArgs()));
    }
    @AfterThrowing(pointcut = "tradeOperations()", throwing = "ex")
    public void logFailure(JoinPoint jp, RuntimeException ex) {
        log.warn("✗ {} : {}", jp.getSignature().getName(), ex.getMessage());
    }
}
Dépendance : spring-boot-starter-aspectj. Aucune ligne de TradeService n'a changé.
08

Lire le pointcut de gauche à droite : execution( type de retour · package.Classe · .méthode · (arguments) ). * = n'importe quoi, (..) = n'importe quels arguments. Donc : toutes les méthodes publiques de TradeService.

En console, un accept donne : « → accept [7, 2] », puis éventuellement « ✗ accept : 409 CONFLICT "Stock insuffisant" ».

Spring Boot 4 : le starter s'appelle spring-boot-starter-aspectj (anciennement spring-boot-starter-aop, nom encore présent dans beaucoup de tutoriels).

JoinPoint donne accès à la méthode appelée et à ses arguments : suffisant pour un log. Attention à ne pas journaliser de données sensibles (mots de passe, plus tard).

AOP · SOUS LE CAPOT

Le même proxy que @Transactional

Même mécanisme, mêmes pièges qu'en séance 3 : un appel interne (this.…) ou une méthode non publique n'est pas intercepté.
09

Rappel séance 3, diapo du proxy : le conteneur injecte un emballage autour de TradeService. @Transactional et notre aspect sont deux couches de ce même emballage.

@After (sans suffixe) s'exécute dans les deux cas, comme un finally. @Around englobe tout et décide lui-même d'appeler la méthode : c'est le bonus du jour.

Pour les curieux : « succès » dans le log ne veut pas forcément dire « commité ». Si notre aspect est à l'intérieur de la transaction, il journalise avant le COMMIT. L'ordre se règle avec @Order, hors programme.

TESTS · STRATÉGIE

Beaucoup de petits tests, quelques gros

Plus on monte, plus le test est réaliste, mais lent et difficile à diagnostiquer quand il échoue.
11

Un test unitaire qui échoue désigne une méthode. Un test d'intégration qui échoue peut venir du JSON, du contrôleur, du service, du SQL… C'est pour ça qu'on en veut moins, mais qu'il en faut.

Le sommet, c'est ce qu'ils font depuis la séance 2 avec curl et leurs fichiers de requêtes. Utile, mais personne ne le relance après chaque modification.

TESTS · RAPPEL SÉANCE 1

L'injection par constructeur rend le service testable

SÉANCE 1 · COUPLAGE FORT
user/UserService.java
public class UserService {
  private final UserRepository users
      = new InMemoryUserRepository();
  // …
}

// Pour tester, impossible de choisir
// le repository : le service le crée
// lui-même. Test = vrai stockage.
AUJOURD'HUI · ON INJECTE UN FAUX
user/UserServiceTest.java
@Test
void createKeepsName() {
  var fake = mock(UserRepository.class);
  when(fake.save(any()))
      .thenAnswer(call -> call.getArgument(0));

  var service = new UserService(fake);
  User user = service.create(new User("Alice"));

  assertEquals("Alice", user.getName());
}
Le service ne sait pas qu'il parle à un faux repository : il ne dépend que de l'interface. Mockito écrit le faux pour nous.
12

C'est l'argument gardé depuis la séance 1 : « impossible à tester ». Le voici. Avec new InMemoryUserRepository() dans le service, aucun moyen de lui glisser autre chose.

Pourquoi Mockito et pas un FakeUserRepository écrit à la main ? Depuis la séance 3, UserRepository étend ListCrudRepository : une dizaine de méthodes à implémenter pour n'en utiliser qu'une. mock() génère l'implémentation, when(…) programme la réponse. Mockito est inclus dans spring-boot-starter-test.

Aucune trace de Spring dans ce test : pas de contexte, pas de base. Il s'exécute en quelques millisecondes. Signatures (create, constructeur de User) à adapter au code du groupe.

TESTS · UNITAIRE

Tester une règle : stock insuffisant, rien n'est écrit

src/test/java/fr/cours/troc/trade/TradeServiceTest.java
@ExtendWith(MockitoExtension.class)
class TradeServiceTest {
    @Mock TradeRepository trades;
    @Mock ItemService itemService;
    @InjectMocks TradeService service;          // construit avec les mocks ci-dessus

    @Test
    void acceptRefusedWhenStockTooLow() {
        // given : Bob n'a plus qu'1 courgette, le troc en demande 4
        when(trades.findById(7L)).thenReturn(Optional.of(proposedTrade(10L, 3, 20L, 4)));
        when(itemService.findById(10L)).thenReturn(new Item(10L, 1L, "tomates", 10));
        when(itemService.findById(20L)).thenReturn(new Item(20L, 2L, "courgettes", 1));
        // when / then
        var ex = assertThrows(ResponseStatusException.class, () -> service.accept(7L, 2L));
        assertEquals(HttpStatus.CONFLICT, ex.getStatusCode());
        verify(trades, never()).save(any());          // rien n'a été écrit
    }
}
Given / when / then : la situation, l'action, le résultat attendu. proposedTrade est une petite méthode utilitaire du test.
13

Le scénario est celui de l'expérience de la séance 3 : Bob a donné ses courgettes ailleurs entre la proposition et l'acceptation.

verify(…, never()) vérifie un comportement, pas seulement un résultat : aucune écriture n'a eu lieu. C'est la preuve que checkStock est bien appelé avant toute écriture.

@InjectMocks appelle le constructeur de TradeService en lui passant les mocks : c'est l'injection par constructeur, faite par Mockito au lieu de Spring. Les dépendances non déclarées en @Mock (un record de propriétés, par exemple) reçoivent null : à déclarer si la méthode testée s'en sert.

Mockito est strict : un when(…) jamais utilisé fait échouer le test. C'est voulu, ça signale un test qui ne teste pas ce qu'il croit.

TESTS · INTÉGRATION

Tester l'API entière, sans lancer de serveur

src/test/java/fr/cours/troc/user/UserApiTest.java
@SpringBootTest                      // démarre tout le contexte Spring
@AutoConfigureMockMvc                // fournit un faux client HTTP
@ActiveProfiles("test")              // application-test.properties : base H2 en mémoire
@Transactional                       // chaque test est annulé à la fin
class UserApiTest {
    @Autowired MockMvc mvc;          // JUnit crée cette classe, pas Spring : on demande l'injection

    @Test
    void createdUserIsListed() throws Exception {
        mvc.perform(post("/users").contentType(MediaType.APPLICATION_JSON)
                                  .content("{\"name\": \"Alice\"}"))
           .andExpect(status().isCreated())
           .andExpect(jsonPath("$.id").isNumber());
        mvc.perform(get("/users"))
           .andExpect(status().isOk())
           .andExpect(jsonPath("$[*].name", hasItem("Alice")));
    }
}
Contrôleur, JSON, service, repository, SQL : toute la chaîne est traversée, comme avec curl.
14

@Autowired : jusqu'ici on n'en avait jamais eu besoin, l'injection par constructeur suffisait. Ici c'est JUnit, pas Spring, qui crée l'objet de test : il faut marquer explicitement ce qu'on veut recevoir. C'est l'usage courant dans les tests, et le seul endroit du cours où on l'utilise.

Spring Boot 4 : @AutoConfigureMockMvc est obligatoire avec @SpringBootTest, et vient de la dépendance de test spring-boot-starter-webmvc-test. Vérifier qu'elle est dans le pom.xml (start.spring.io l'ajoute normalement).

@Transactional sur une classe de test : Spring fait un ROLLBACK à la fin de chaque test au lieu d'un COMMIT. Les tests ne se polluent pas entre eux. Ça marche avec MockMvc parce que la requête s'exécute dans le même thread.

Adapter le code de statut attendu (201 ou 200) à ce que le groupe a choisi en séance 2.

TESTS · QUE TESTER, ET OÙ ?

Chaque chose à son étage

  • Règles métier stock insuffisant, mauvais destinataire, troc déjà exécuté → unitaire
  • Le contrat HTTP URL, JSON, codes de statut 201, 404, 409 → intégration

Critère de notation « détail des choix techniques » : pouvoir dire pourquoi tel test est unitaire et tel autre d'intégration est exactement ce qu'on attend.

Un bon nom : acceptRefusedWhenStockTooLow. Un mauvais : test1. Quand il passe au rouge dans six mois, le nom doit dire ce qui est cassé.

Le test du rollback est un excellent bonus : il transforme l'expérience manuelle de la séance 3 en preuve reproductible.

CHECKPOINT #1 · PIÈGES COURANTS

Le log n'apparaît pas : pourquoi ?

  • Pointcut faux une faute dans le package : aucune erreur, aucun log. Le piège n° 1.
  • Pas de @Component l'aspect n'est pas un bean : Spring ne le connaît pas
  • @Aspect introuvable dépendance spring-boot-starter-aspectj absente du pom.xml
  • Appel interne this.transfer() depuis accept() ne traverse pas le proxy
  • Pour vérifier un point d'arrêt dans l'advice, application lancée en debug
18

Pointcut faux : le plus traître, car tout démarre normalement. Vérifier le package complet (fr.cours.troc.trade) et le nom de la classe, à la majuscule près. IntelliJ Ultimate affiche une icône dans la marge des méthodes interceptées ; en Community, le point d'arrêt reste le plus sûr.

Appel interne : si un groupe veut tracer transfer(), il faut qu'elle soit appelée depuis un autre bean. Sinon, accepter de ne tracer que les méthodes appelées par le contrôleur, ce qui est en général le bon niveau.

CHECKPOINT #1 · TRANSITION

Une base rien que pour les tests

  • Base séparée src/test/resources/application-test.properties → jdbc:h2:mem:troc-test
  • Dépendances spring-boot-starter-test et spring-boot-starter-webmvc-test, en scope test
  • Emplacement src/test/java, dans le même package que la classe testée
  • Lancer flèche verte d'IntelliJ, ou ./mvnw test dans le terminal
  • La règle tous les tests au vert avant chaque commit
19

Sans base séparée, les tests d'intégration écrivent dans ./data/troc : les données de démonstration se retrouvent mélangées aux données de test. Le profil test (séance 2, ordre de priorité des sources) surcharge seulement l'URL ; le reste d'application.properties s'applique toujours.

Piège : un fichier nommé application.properties dans src/test/resources remplace entièrement celui de main (mêmes nom et chemin sur le classpath). D'où le choix d'un profil.

Même package : le test peut accéder aux méthodes package-private, et IntelliJ range les tests à côté de leur classe.

TP · EN AVANCE

@Around : l'advice qui décide d'appeler la méthode

trade/TradeLoggingAspect.java
@Around("tradeOperations()")
public Object timed(ProceedingJoinPoint jp) throws Throwable {
    long start = System.nanoTime();
    try {
        return jp.proceed();                    // appelle la vraie méthode
    } finally {
        long ms = (System.nanoTime() - start) / 1_000_000;
        log.info("⏱ {} : {} ms", jp.getSignature().getName(), ms);
    }
}
Oublier proceed() : la méthode n'est jamais exécutée, sans aucune erreur. Le plus puissant des advices, et le plus dangereux.
21

Diapo pour les groupes en avance, à montrer individuellement plutôt qu'à toute la salle.

@Around peut aussi modifier les arguments, la valeur de retour, ou avaler une exception. C'est exactement comme ça que @Transactional est écrit : BEGIN, proceed(), puis COMMIT ou ROLLBACK.

Prolongement possible : une annotation maison @Timed et un pointcut @annotation(fr.cours.troc.Timed), pour choisir méthode par méthode.
