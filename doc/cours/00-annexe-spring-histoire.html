Spring Framework : le conteneur IoC de la séance 1, plus des modules (AOP en séance 4, Web MVC pour nos contrôleurs, transactions en séance 3).

Les projets de l'écosystème sont des bibliothèques séparées qui s'appuient sur le framework. Dans le cours : Spring Data JDBC (séance 3), Spring Security en bonus (séance 4).

PARTIE 01 · SPRING BOOT

Ce que Spring Boot ajoute

  • Starters une dépendance tire tout le nécessaire, en versions compatibles
  • Auto-configuration Spring Web présent ? Boot configure serveur et JSON tout seul
  • Serveur embarqué Tomcat est inclus : on lance un main, rien à installer
  • JAR exécutable java -jar troc-api.jar, en local comme en production
  • Configuration externe application.properties, variables, profils (séance 2)
  • Actuator /actuator/health, métriques : l'appli prête pour la prod
04

Principe général : « convention plutôt que configuration ». Boot fait un choix par défaut, on ne configure que ce qui diffère.

L'auto-configuration n'est pas magique : elle regarde ce qui est présent sur le classpath et dans la configuration, et crée des beans en conséquence. On peut toujours remplacer un bean auto-configuré par le sien.

Actuator n'est pas utilisé dans le TP ; c'est une piste de bonus facile (une dépendance à ajouter).

PARTIE 02 · JAVA

Trente ans de Java en neuf dates

Depuis 2018 : une version tous les six mois, et une LTS (support long) tous les deux ans. Les entreprises passent d'une LTS à l'autre.
07

Java 5 (2004) est la date clé pour Spring : sans annotations dans le langage, pas de @Service ni de @Repository. Spring a donc commencé en XML.

2010 : Oracle rachète Sun et devient le gardien de Java. Le développement se fait en open source dans OpenJDK ; Oracle, Eclipse (Temurin), Amazon, Azul… distribuent des JDK construits à partir de ce même code.

Java 26 est sorti en mars 2026, Java 27 en septembre 2026. Ce sont des versions à support court : la prochaine LTS attendue est Java 29, en septembre 2027.

PARTIE 02 · LE CONTEXTE

Pourquoi Spring est né

  • J2EE, fin des années 90 le code métier s'écrit en EJB, exécutés par un serveur lourd
  • Tester ? quasi impossible sans démarrer tout le serveur
  • 2002, Rod Johnson un livre qui propose de faire plus simple, avec du code à l'appui
  • L'idée des objets Java ordinaires (POJO), assemblés par un conteneur léger
  • Le cœur du projet l'inversion de contrôle, exactement celle de la séance 1
08

Un EJB de l'époque imposait plusieurs interfaces techniques, un descripteur XML et un serveur d'application pour simplement exister. Le code métier était noyé dans le code technique.

POJO = Plain Old Java Object : une classe Java normale, sans héritage ni interface imposés par un framework. Notre UserService en est un.

J2EE n'a pas disparu : devenu Java EE puis Jakarta EE, il fournit des standards (Servlet, Bean Validation…) que Spring utilise lui-même. Tomcat, le serveur embarqué par Boot, implémente la norme Servlet de Jakarta EE.

Un EJB (Enterprise JavaBean) : un composant métier exécuté par un serveur d'application. Deux interfaces, une classe, un fichier XML… pour une seule ligne utile, en vert.
09

Définition : un EJB est un composant Java côté serveur, défini par la norme J2EE. Il ne s'exécute pas seul : il est déployé dans un serveur d'application (WebLogic, WebSphere, JBoss…) qui contient un « conteneur EJB ». Ce conteneur lui fournit gratuitement des services techniques : transactions, sécurité, appels à distance depuis une autre machine, réutilisation des instances.

L'idée était bonne (le conteneur gère la technique, le développeur écrit le métier), c'est ce que fait Spring aujourd'hui. Le problème était le prix à payer : chaque composant implémentait des interfaces imposées (les méthodes en rouge, presque toujours vides), se déclarait dans un fichier ejb-jar.xml, et ne pouvait être testé qu'une fois déployé sur le serveur.

Trois sortes d'EJB : session (un service, comme ici), entity (une donnée persistée en base, ancêtre lointain de nos entités) et message-driven (traitement de messages).

Côté client, pas d'injection : on allait chercher l'EJB soi-même dans un annuaire (JNDI), puis on appelait home.create(). C'est exactement l'inverse de l'inversion de contrôle de la séance 1.

Suite de l'histoire : EJB 3 (2006) s'est fortement simplifié en s'inspirant de Spring et Hibernate (annotations @Stateless, classes ordinaires). Les EJB existent toujours dans Jakarta EE, sous le nom Jakarta Enterprise Beans, mais on en écrit rarement dans un nouveau projet.

PARTIE 02 · SPRING

Vingt ans de Spring en neuf dates

Plus de vingt ans, et toujours la même idée au centre : le conteneur IoC. Seule la façon de le configurer a changé : XML, puis annotations, puis Boot.
10

Spring 2.5 (2007) introduit @Component et @Autowired : il a fallu attendre Java 5 pour que ce soit possible.

Spring 3.0 (2009) apporte la configuration en classes Java (@Configuration, @Bean), alternative au XML, et le support REST dans Spring MVC.

Les propriétaires successifs : Interface21, renommée SpringSource, rachetée par VMware (2009), passée chez Pivotal (2013), revenue chez VMware (2019), elle-même rachetée par Broadcom (2023). Spring reste open source.

Spring Boot 4.1 est sorti en juin 2026 ; c'est la version utilisée dans le cours.

PARTIE 03 · JAVA MODERNE

Ce que Java a gagné depuis Java 8

  • var · Java 10 le type d'une variable locale est déduit
  • switch · Java 14 un switch qui renvoie une valeur, sans break
  • Text blocks · Java 15 des chaînes multilignes, pratiques pour SQL et JSON
  • Records · Java 16 une classe de données immuable en une ligne
  • Threads virtuels · Java 21 des milliers de requêtes en parallèle, à moindre coût
  • main compact · Java 25 void main() sans classe : Java plus simple à apprendre
12

Les records sont déjà utilisés dans le cours : ItemProperties et ProposeTradeRequest en séance 2. Les text blocks seront pratiques pour les requêtes SQL de la séance 3.

Threads virtuels : Spring Boot les active avec une seule propriété, spring.threads.virtual.enabled=true. Pas nécessaire pour le projet, mais bon sujet de bonus ou de présentation.

Java 25 finalise aussi les imports de modules et les corps de constructeurs flexibles (du code avant l'appel à super), moins utiles dans notre contexte.

PARTIE 03 · JAVA MODERNE

Java moderne, appliqué au troc

exemples · fil rouge
// Java 16 · record : constructeur, accesseurs, equals, toString générés
public record Item(Long id, String name, int quantity, Long ownerId) { }

// Java 10 · var : le type List<Item> est déduit
var items = itemService.findAll(ownerId);

// Java 14 · switch expression : il renvoie une valeur
String label = switch (trade.getStatus()) {
    case PROPOSED -> "en attente";
    case ACCEPTED -> "validé";
    case EXECUTED -> "exécuté";
};

// Java 15 · text block : une chaîne sur plusieurs lignes (séance 3)
String sql = """
    SELECT * FROM item
    WHERE owner_id = ?
    """;
13

Le switch expression oblige à traiter tous les cas de l'enum : si on ajoute un statut à TradeStatus sans mettre à jour le switch, le code ne compile plus. C'est une sécurité.

Un record ne convient pas à tout : il est immuable, donc pas de setters. Parfait pour une requête ou une configuration, à réfléchir pour une entité dont l'état change (le statut d'un Trade).

PARTIE 03 · SPRING BOOT 3 · NOVEMBRE 2022

Spring Boot 3 : le grand saut de 2022

  • Java 17 minimum fin de Java 8 et 11 pour les projets Spring récents
  • javax.* → jakarta.* les imports Jakarta EE changent de nom de paquet
  • Images natives compilation GraalVM : démarrage en quelques millisecondes
  • Observabilité métriques et traces unifiées avec Micrometer
  • Boot 3.2 (2023) threads virtuels et nouveau client HTTP RestClient
14

Le changement javax → jakarta vient du transfert de Java EE à la fondation Eclipse, qui n'avait pas le droit de garder le nom de paquet javax. Concrètement : import javax.servlet… devient import jakarta.servlet…

Réflexe à donner aux étudiants : un tutoriel qui importe javax.* date d'avant 2022 (Spring Boot 2). L'idée reste valable, le code est à adapter.

Les images natives ne sont pas utilisées dans le cours ; c'est ce qui permet à Spring de rivaliser avec des frameworks comme Quarkus ou Micronaut sur le temps de démarrage.

PARTIE 03 · SPRING 7 & BOOT 4 · NOVEMBRE 2025

Spring Boot 4 et 4.1 : la génération actuelle

  • JSpecify @Nullable standardisé : l'IDE signale les null oubliés
  • Jackson 3 nouvelle version de la conversion JSON par défaut
  • Boot modularisé découpé en modules fins : on n'embarque que l'utile
  • Versions d'API @GetMapping(version = "2") : versionner une API REST
  • Résilience @Retryable et @ConcurrencyLimit intégrés au cœur
  • Boot 4.1 · juin 2026 gRPC, OpenTelemetry, plus de réglages Jackson
15

Spring Boot 4 garde Java 17 comme minimum, mais supporte pleinement Java 25. Il passe aussi sur Jakarta EE 11 et Tomcat 11.

Jackson 3 : la partie principale change de paquet (tools.jackson au lieu de com.fasterxml.jackson). Les annotations courantes comme @JsonProperty gardent leur paquet. Encore un piège classique avec les tutoriels plus anciens.

Le versioning d'API et les clients HTTP déclaratifs (une interface Java annotée qui devient un client REST) sont de bonnes pistes de bonus pour les groupes en avance.

@Retryable relance automatiquement une méthode qui a échoué : intéressant à évoquer en séance 4, car il repose sur l'AOP.

PARTIE 03 · CHOISIR SES VERSIONS

Quelle version choisir ?

Le cours : Java 25 LTS (support long) + Spring Boot 4.1 (dernière génération). Deux versions en vert : celles à préférer pour un projet qui démarre aujourd'hui.
16

LTS = Long-Term Support : des correctifs de sécurité pendant des années. Les versions intermédiaires (26, 27) ne sont maintenues que six mois, jusqu'à la suivante.

Spring Boot sort une version mineure environ tous les six mois. Chaque version est maintenue gratuitement pendant une durée limitée, puis il faut monter de version (ou payer un support commercial).

Le choix des versions est un bon exemple de « choix technique à justifier » pour l'évaluation : pourquoi une LTS plutôt que la toute dernière version de Java ?
